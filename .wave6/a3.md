# Wave-6 Auditor A3 — Platform / Technical

Evidence = actual code reads (file:line).

## Gaps

### A3-01 — No GDPR data-subject export (DSAR): a rider asks "what do you hold on me" and nobody can answer from the system
- **Scenario:** A rider files an access request. Their data is scattered
  across `commerce.fare_payments`, `commerce.loyalty_*`,
  `citizen.drt_requests`, carbon receipts — each keyed by the Keycloak
  `sub`. There is no endpoint, no export job, no documented procedure to
  assemble it. GDPR Art. 15 gives 30 days.
- **Why unhandled:** grep `gdpr|dsar|erasure|data subject` across services =
  zero code hits (docs only).
- **Recommended fix:** citizen-api `GET /v1/me/data-export` (JWT, self):
  aggregates the rider's rows from every domain table into one JSON
  document; audited via audit-log.
- **Size:** M · **Class:** FIX-NOW

### A3-02 — No erasure/anonymization path — and the tension with the immutable audit log is unresolved
- **Scenario:** A rider exercises Art. 17 (right to erasure). Payments and
  DRT history keep their `rider_sub` forever; the hash-chained audit log
  (by design) cannot be rewritten. Nobody has defined what erasure means
  here.
- **Why unhandled:** no anonymization code anywhere; docs/INSIDER_THREAT.md
  covers audit immutability but not the erasure reconciliation.
- **Recommended fix:** pseudonymization design (rider_sub is already a
  pseudonymous Keycloak sub — not a name): erasure = (a) delete/disable the
  Keycloak account, (b) `POST /v1/me/erasure` tombstones the linkability by
  rewriting domain rows to `erased:<sha256(sub+salt)[:12]>` so per-rider
  analytics survive but identity is unrecoverable, (c) audit-log entries
  stay (they hold the pseudonymous sub, which no longer resolves to a
  person) — documented in docs/GDPR.md.
- **Size:** M · **Class:** FIX-NOW

### A3-03 — No outbound webhooks: partner systems must poll or get Kafka access
- **Scenario:** The city's 112 CAD system and the transport authority's
  dashboard need to know *immediately* when a critical safety incident
  opens. Today their choices: poll `GET /v1/incidents`, or get internal
  Kafka access (never acceptable for externals).
- **Why unhandled:** grep `webhook` = only the *inbound* H2 sensor webhook
  (`infra-api/cmd/server/main.go:110`).
- **Recommended fix:** migration 0009 `infra.webhook_subscriptions`
  (url, secret, event filter, active); infra-api signs each delivery
  (HMAC-SHA256, `X-H2Fleet-Signature`) and POSTs on incident
  open/escalate/resolve + high/critical severity; bounded retries, delivery
  log table.
- **Size:** M · **Class:** FIX-NOW

### A3-04 — Single-tenant throughout: a second operator or a second city cannot be isolated
- **Scenario:** The platform is a success; the region asks to run the
  neighboring city's 12 buses on the same deployment, or a private
  sub-operator runs 5 of the 50 buses. Every query is global: any
  `operator` JWT sees all vehicles, all stations, all payments.
- **Why unhandled:** one Permify tenant (`permify.go:86` default `t1`), one
  Keycloak realm, no `operator_id`/`tenant_id` column on any domain table,
  no query scoping anywhere.
- **Recommended fix:** DECISION — single-municipality deployment is the
  stated product scope (SPEC.md). Document the sharding path
  (deployment-per-city, realm-per-city) and the in-product tenancy cost;
  do not bolt on half-tenancy.
- **Size:** — · **Class:** DECISION (documented)

### A3-05 — Retention is defined for telemetry and backups only; nothing else has a lifecycle
- **Scenario:** Seven years in, `commerce.fare_payments` holds millions of
  rows of personal payment data with no legal basis to keep it all; an
  auditor asks for the retention schedule and the platform's answer covers
  2 of ~40 tables.
- **Why unhandled:** only `fleet.telemetry` (90 d, 0004) and backups (14 d,
  infra/backup/README.md:13) have retention.
- **Recommended fix:** docs/DATA_RETENTION.md: per-table schedule (payments
  10 y fiscal / pseudonymized after rider erasure, DRT trips 24 mo,
  incidents 10 y safety regulation, audit-log WORM indefinite, loyalty
  account lifetime) + the erasure hook (A3-02) as the enforcement
  mechanism. Table-driven doc, no silent deletes in code.
- **Size:** S · **Class:** FIX-NOW (doc + erasure hook)

### A3-06 — API versioning exists (/v1) but there is no deprecation/sunsetting policy
- **Scenario:** Wave-5 renamed telemetry semantics; a future /v2 will break
  mobile clients. Nothing states how long /v1 lives or how clients are
  notified.
- **Why unhandled:** docs/API.md documents routes, not lifecycle.
- **Recommended fix:** add a versioning & deprecation section to docs/API.md
  (Sunset header, ≥2-release overlap, event-contract additive-only rule).
- **Size:** S · **Class:** FIX-NOW (doc)

### A3-07 — DR restore is a documented manual drill; nothing proves a backup restores until the quarter someone tries
- **Scenario:** Backup job green for 90 days; the first restore attempt
  discovers the dump is corrupt / the TigerBeetle data file was copied
  while the service was running.
- **Why unhandled:** docs/DR.md is a procedure; infra/backup runs pg_dump;
  no automated restore-verification step (e.g., nightly restore into an
  ephemeral Postgres + row-count checksum).
- **Recommended fix:** CONTRACT — automated restore-proof requires the
  Docker host; add the verification script to infra/backup and wire it into
  the DR doc as the drill's step 0. (Script added this wave.)
- **Size:** S · **Class:** CONTRACT (script + doc)

### A3-08 — Secrets rotation procedure exists but service tokens have no dual-credential rollover
- **Scenario:** Rotating `AUDIT_INGEST_TOKEN` (used by 7 services to write
  audit events) requires every service to restart simultaneously — any lag
  = lost audit events or 401 storms.
- **Why unhandled:** `RequireIngestAuth` (`audit-log/internal/handlers/
  handlers.go:171`) accepts exactly one token.
- **Recommended fix:** accept a comma-separated token list (old + new during
  the window) — standard dual-credential rollover. S.
- **Size:** S · **Class:** FIX-NOW

### A3-09 — PWA works offline read-only; queued actions are silently impossible
- **Scenario:** An inspector underground opens the incident detail (cached
  shell works — vite-plugin-pwa precache + tile cache,
  `apps/pwa/src/pwa-utils.ts`), tries to acknowledge an incident, and gets
  a network error; the ack is lost rather than queued.
- **Why unhandled:** no background-sync / outbox in the PWA.
- **Recommended fix:** DECISION — read-only offline + explicit error is an
  honest degraded mode for an ops console; document it. (Queued mutations
  need conflict semantics — a product decision, not a gap fix.)
- **Size:** — · **Class:** DECISION (documented)
